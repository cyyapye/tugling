# Private evaluation rubric

Judge only the assessment response and its adherence to the request. Equivalent well-supported findings are acceptable; do not require a particular vocabulary or a fixed component architecture.

1. **Grounded inventory and completeness:** Identifies the public booking form, host list/filter/arrival action/print path, and arrival screen from actual source. Distinguishes working local interactions from the absent backend, authentication and cross-device synchronization. Does not invent additional pages, delivery behavior, a framework or production readiness.
2. **Existing reuse and justified boundaries:** Recognizes shared CSS variables, `.panel`, `.button` variants, `.field`, status styling and shared browser-storage helpers. Recommends appropriate reuse for a future host handover screen while preserving the kiosk’s large controls, contrast and focused navigation. Does not equate the intentionally distinct kiosk presentation with an automatic need to make every page identical or to migrate frameworks.
3. **Operationally meaningful gaps:** Prioritizes at least two concrete issues supported by source and usage context, including a kiosk/desk issue: successful kiosk check-in leaves the previous guest’s name visible indefinitely; an already-open host page does not refresh after another page updates storage; separate physical devices cannot share localStorage; or host phone use currently depends on horizontally scrolling a wide table. Distinguishes implementation evidence from untested visual or accessibility claims.
4. **Actionable next-step recommendations:** Gives a small ordered set of recommendations connected to the planned shift handover and existing paper progress notes. Treats handover’s task/status/ownership needs as decisions to clarify rather than claiming that the current arrival status already captures repair progress. Avoids a generic exhaustive component checklist or proposing a large design-system rewrite without evidence.
5. **Scope and evidence discipline:** Does not edit project files, install dependencies, implement the handover screen, or report unperformed browser/testing evidence. Any setup artifact or configuration suggestion remains a recommendation because the user asked for assessment only. If inspection is source-only, clearly limits claims about rendered layout and interaction quality.
